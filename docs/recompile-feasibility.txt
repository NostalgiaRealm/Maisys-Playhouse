Maisy's Playhouse (1999): preliminary x86-to-WebAssembly feasibility
Investigation date: 2026-11-11
Scope: static disc/binary inspection and read-only examination of the existing A2 recompiler. No Maisy port, build, original-game execution, or browser gameplay test was performed.

Conclusion
----------
Static x86-to-WebAssembly recompilation is technically plausible and worth an early interactive proof. The executable and six plug-ins are conventional PE32 Intel x86 modules with ordinary code sections and relocation data; they are suitable inputs for further native analysis. This does not establish complete instruction coverage or prove that the game can already run in the browser.

The A2 recompiler offers a substantial starting point for instruction translation, but it is not a general Win32 compatibility layer. Maisy would require substantial new module-loading, callback, GDI, WinMM/media, and browser-scheduling support. No evidence found here justifies claiming a drop-in conversion or guaranteed performance.

An existing public/game/spel.wasm artifact is present, 6,488,409 bytes. Its presence was confirmed; it was not launched or rebuilt.

The source implements Python/Capstone static x86 instruction lifting with a custom Wasm encoder and Ghidra function inventory. It retains original addresses in linear memory and dispatches imported services to JavaScript. It does not compile recovered C.

Concrete reuse blockers:
- recompile.py lines 74-87 define a fixed layout and MEM_PAGES=4096 (256 MiB). Every Maisy plug-in's preferred base begins at or beyond the end of that memory.
- Its code-address lookup is dense over a game-specific range. Extending that naively across separated plug-in bases would waste large amounts of memory.
- recompile.py around lines 120-153 assumes a .text section and named imports. Main and plug-in code discovery/linking must be adapted.
- build.py around lines 285-295 hard-codes A2 input and function-inventory paths.
- win32.js lines 131-132 return zero for LoadLibraryA/GetProcAddress.
- win32.js around lines 678-692 handles only a small GDI debug-text subset. It is not Maisy's bitmap/palette renderer.
- A2's browser-loop, exceptions, x87 model, and replacement addresses are specific to A2. They cannot be transferred as universal runtime semantics.

Candidate architecture
----------------------
Lift the original player and required plug-ins, preserving authored .mfx/.mxx content. Supply a proper module/export/callback bridge, measured memory/relocation scheme, browser-friendly scheduler, GDI presentation, audio/media support, and virtual filesystem/persistence.

An alternative is an mTropolis-compatible content runtime compiled to Wasm. This preserves original data/scripts but is not recompilation of the original x86 player. Prefer the original-code approach first and base any fallback on concrete blockers.

Remaining unknowns
------------------
Actual startup sequence after autorun/install, required plug-in subset, dynamically resolved services, callbacks, instruction/exception coverage, native rendering dimensions, media codecs, copy/protection paths if any, precise activity behavior, and mobile performance remain unverified.

No claim is made that the recompile already works or that 30 FPS has been achieved. The smallest useful next step, once implementation is requested, is an interactive original scene with input, sound, required plug-ins, and correct browser yielding.
