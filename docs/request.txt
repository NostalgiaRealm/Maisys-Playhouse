3. **Established findings: use the actual Maisy architecture**

   A preliminary static investigation on 2026-11-11 established:

   - No file named `spel.dat` appears in this ISO's filesystem inventory. That filename belongs to the A2 reference.
   - The main program is `z_data/Maisy.exe`, a 1,085,952-byte PE32 Intel x86 executable.
   - Its version resource identifies the **mTropolis 32-Bit Windows Player, version 2.0**, from mFactory/Quark, with original filename `mTplay32.exe`.
   - The main data files are `z_data/data.mfx` (4,588,716 bytes) and `data2.mxx` at the disc root (294,743,286 bytes).
   - Six native x86 plug-ins are supplied under `z_data/mPlugins/`: `BASIC.X32`, `Bitmap.r32`, `CURSORS.C32`, `EXPRMNTL.R32`, `EXTRAS.R32`, and `NETWORK.R32`.
   - The main executable has 449 static import entries, including extensive USER32/GDI32 use and WinMM audio. Its static import table does not contain DirectDraw or Direct3D. QuickTime/Video for Windows names also occur in its strings; their actual use by this title remains to be established.
   - The supplied files match the English Windows release's executable/data size and prefix-hash fingerprints in ScummVM's mTropolis detection table. That table marked this title unimplemented/unsupported when checked; recognition is not working support.

   These are static findings, not proof that a browser port or recompiled module runs. Preserve the supplied edition's language and media. Do not assume Maisy uses A2's Direct3D engine, vehicle systems, memory layout, or startup flow.

   Maisy contains a multimedia runtime plus authored content. Identify the boundary between native player/plug-in code and the objects, scripts, scenes, and media in the data files. Keep authored content intact wherever possible.

4. **Preferred approach: recompile the original x86 runtime to WebAssembly**

   The A2 reference has an actual static binary recompiler: Python/Capstone decodes the original x86 program, uses a Ghidra function inventory, and emits WebAssembly directly through a custom encoder. It is not compilation of decompiler-generated C.

   Start with these reference files:

   - `docs/recompiler.md`
   - `tools/recomp/recompile.py`
   - `tools/recomp/lift.py`
   - `tools/recomp/wasmgen.py`
   - `tools/recomp/build.py`
   - `tools/recomp/replacements.py`
   - `source/host/machine.js`
   - `source/host/win32.js`
   - `source/host/vfs.js`
   - `source/host/persist.js`

   Reuse compatible instruction translation, control-flow handling, virtual memory, host-call dispatch, and file/persistence infrastructure. Create Maisy-specific configuration and source copies. Do not copy A2 addresses, owner patches, physics changes, timing hooks, or other game-specific replacements into Maisy.

   Recompile `Maisy.exe` and the plug-ins whose native behavior is required. Preserve original data layouts, calling conventions, script behavior, and state transitions. Establish function boundaries and indirect-call targets from binary evidence; document unsupported instructions and reachable gaps explicitly.

   Solve these known differences:

   - **Multiple modules:** implement the required module loading, initialization, export lookup, cross-module calls, and callbacks. A2's `LoadLibraryA` and `GetProcAddress` implementations currently return zero and cannot load Maisy's plug-ins.
   - **Address space:** Maisy's plug-ins have preferred bases from `0x10000000` through `0x15000000`, outside A2's fixed 256 MiB linear memory. Choose a justified memory layout or correct PE relocation strategy. Adapt code-address lookup for separated module ranges instead of copying A2's dense lookup layout across enormous address gaps.
   - **Windows services:** implement the actually required window/message, input, resource, timer, file, registry, heap, and synchronization behavior. Determine callback and exception requirements from reachable code.
   - **2D rendering:** build a faithful GDI/bitmap/palette presentation layer. A2's small GDI debug-text stubs are insufficient. Preserve clipping, drawing order, transparency, raster operations, fonts, and coordinate mapping where used.
   - **Audio/media:** support the WinMM calls and media formats used by this title. Determine whether QuickTime, Video for Windows, MIDI, or other dynamically resolved services are required rather than assuming every runtime capability is exercised.
   - **Browser scheduling:** identify Maisy's own message-loop and wait points so execution yields to the browser without changing game timing. Do not copy A2's race-loop replacements.
   - **Runtime details:** handle required x87 behavior, calling conventions, stack probes, exceptions, and other compiler/runtime helpers. A2's specific workarounds are starting evidence, not general compatibility guarantees.

   Do not silently replace required APIs with success-returning stubs, drop plug-in behavior, or skip unsupported reachable functions just to obtain a picture.
